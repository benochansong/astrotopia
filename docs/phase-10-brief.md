## 1. 프로젝트 개요

ASTROTOPIA는 2D 횡스크롤 액션 RPG에 우주 탐험, 생존, 자원 채굴, 장비 제작, 기지 건설, 산업 자동화 및 행성 개척을 결합한 독창적인 SF 게임이다.

이전 개발 단계의 목표는 다음과 같다.

- Phase 1 — THE FIRST LANDING: 횡스크롤 엔진 및 EDEN 행성
- Phase 2 — BATTLE EVOLUTION: 전투, 무기, 스킬 및 보스
- Phase 3 — SURVIVAL PROTOCOL: 생존, 채굴, 정제, 제작 및 연구
- Phase 4 — COLONY RISING: 기지 건설, 발전 및 산업 자동화
- Phase 5 — BEYOND EDEN: 우주선 수리, 행성 이동 및 다중 기지
- Phase 6 — EXTREME WORLDS: 극한 환경, 수중 이동 및 제트팩
- Phase 7 — PATH OF THE EXPLORER: 직업, 전직, 전문화 및 궁극기
- Phase 8 — ANCIENT SECRETS: OMEGA, 고대 문명, 최종 보스 및 엔딩
- Phase 9 — GALACTIC CIVILIZATION: 무역, 자동 물류, 도시 발전 및 우주 정거장

Phase 10에서는 기존 싱글플레이 게임을 유지하면서 온라인 협동 및 공동 행성 개척 시스템을 추가한다.

플레이어들이 각자의 직업과 전문성을 활용하여 함께 전투하고, 탐험하고, 기지를 건설하며, 새로운 문명을 발전시킬 수 있도록 한다.

개발 시작 전에 현재 ASTROTOPIA 프로젝트의 실제 구현 상태를 분석한다.

다음 항목을 확인한다.

- 게임 엔진 및 기술 스택
- 현재 프로젝트 실행 방식
- 캐릭터 이동 및 물리 엔진
- 전투 및 피해 판정
- 몬스터 AI
- 보스 전투
- 직업 및 스킬
- 행성 이동
- 우주선 및 화물
- 인벤토리
- 아이템 획득
- 장비 제작
- 기지 건설

- 정착민 및 도시 발전

온라인 협동에 반드시 필요한 기능을 우선 보완한다.

## 3. 멀티플레이 설계 철학

ASTROTOPIA는 단순히 다른 플레이어의 캐릭터가 화면에 보이는 게임이 되어서는 안 된다.

플레이어들이 실제로 함께 행동하고 서로의 전문성을 활용할 수 있어야 한다.

핵심 협동 구조:

공동 탐험 → 역할 분담 → 외계 생명체 전투 → 자원 수집 → 공동 기지 건설 → 기술 연구 → 공동 산업 생산 → 새로운 행성 탐험 → 협동 보스 공략 → 문명 발전

다음 원칙을 적용한다.

- 싱글플레이를 계속 지원한다.
- 혼자서도 메인 스토리를 완료할 수 있다.
- 멀티플레이에서는 협동의 재미를 추가한다.
- 특정 직업을 반드시 포함해야만 게임을 진행할 수 있는 구조를 만들지 않는다.
- 친구끼리 서로 다른 플레이 스타일로 활동할 수 있도록 한다.
- 다른 플레이어의 기지와 아이템을 무단으로 훼손할 수 없도록 한다.
- 불필요한 경쟁 및 강제 PvP를 도입하지 않는다.
- 접속하지 않은 플레이어에게 과도한 불이익을 주지 않는다.

초기 목표는 안정적인 소규모 온라인 협동 게임이다.

대규모 MMORPG 서버는 이번 단계의 필수 범위에서 제외한다.

## 4. 게임 모드 구성

기존 메인 메뉴를 확장한다.

### MODE 01 — SINGLE PLAYER

싱글플레이.

- 기존 게임 방식 유지
- 기존 저장 데이터 사용
- 인터넷 연결 없이 플레이 가능한 기존 기능 유지
- 개인 행성 탐험
- 개인 기지 건설
- 개인 스토리 진행
- 개인 문명 발전

### MODE 02 — PRIVATE CO-OP

비공개 온라인 협동.

- 친구 초대 코드
- 2~4인 플레이
- 공동 세계
- 공동 기지
- 협동 전투
- 공동 자원 수집 및 산업 운영

### MODE 03 — PUBLIC EXPLORATION

공개 탐험.

- 다른 플레이어와 탐험대 구성
- 공개 로비
- 공동 탐험 임무
- 제한적인 협동 전투
- 공개 보스 도전

공개 탐험은 비공개 협동이 안정적으로 작동한 이후 구현한다.

### MODE 04 — COLONY VISIT

기지 방문.

- 친구가 건설한 기지 방문
- 도시 및 산업 시설 구경
- 허용된 시설 이용
- 자원 및 장비 거래
- 방문자 권한에 따른 제한

각 게임 모드의 데이터 저장 방식과 적용되는 권한을 명확하게 구분한다.

## 5. 초기 멀티플레이 규모

이번 단계의 기본 개발 목표:

- 최소 동시 접속 인원: 2명
- 초기 권장 접속 인원: 2~4명
- 확장 목표: 8명
- 장기 확장 목표: 16명 이상의 공동 세계

동시 접속 인원에 관한 수치는 실제 서버 성능과 네트워크 테스트 결과에 따라 조정한다.

처음부터 대규모 서버를 구축하지 않는다.

2명의 플레이어가 실제로 연결되어 정상적으로 움직이고, 싸우고, 아이템을 획득하고, 공동 기지를 건설하는 기능을 먼저 완성한다.

이후 4인 협동으로 확장한다.

동일한 브라우저에서 가짜 플레이어를 생성하는 방식으로 실제 온라인 멀티플레이가 구현되었다고 보고하지 않는다.

## 6. 멀티플레이 기술 구조

기존 프론트엔드 기술 스택을 유지한다.

기존 프로젝트가 Phaser, TypeScript, Vite 기반이라면 해당 구조를 최대한 재사용한다.

권장 서버 기술:

- Node.js
- TypeScript
- WebSocket 기반 실시간 통신
- 서버 측 게임 상태 관리
- 개발용 데이터베이스
- 운영 환경에서 사용할 영구 데이터베이스
- 서버 측 저장 및 복원

WebSocket 구현은 기존 프로젝트 구조와 호환성을 검토하여 Colyseus, Socket.IO 또는 적절한 WebSocket 라이브러리 중 하나를 선택한다.

여러 네트워크 프레임워크를 불필요하게 혼합하지 않는다.

권장 프로젝트 구조:

```text

│   ├── scenes/
│   ├── entities/
│   ├── systems/
│   ├── network/
│   ├── ui/

│   ├── auth/
│   ├── rooms/
│   ├── worlds/
│   ├── simulation/
│   ├── combat/

```

위 구조는 권장 예시다.

현재 프로젝트에 적합하다면 별도의 서버 디렉터리만 추가하는 방식으로 개발한다.

기존 싱글플레이 프로젝트를 위 구조에 맞추기 위해 전면 이동하거나 재작성하지 않는다.

## 7. 서버 권한 기반 게임 구조

온라인 게임에서는 서버를 최종 게임 상태의 권한자로 설정한다.

SERVER-AUTHORITATIVE ARCHITECTURE.

클라이언트는 플레이어의 입력을 서버에 전달한다.

서버는 해당 입력이 유효한지 확인하고 실제 게임 결과를 계산한다.

서버가 관리해야 하는 항목:

- 플레이어 위치
- 이동 가능 여부
- 체력 및 에너지
- 공격 판정
- 스킬 사용
- 재사용 대기시간
- 몬스터 상태
- 보스 상태
- 아이템 드롭
- 경험치 지급
- 인벤토리
- 크레딧
- 제작 및 강화
- 건물 배치
- 자원 소비
- 공동 창고
- 자동 생산
- 화물 운송
- 플레이어 간 거래
- 퀘스트 보상

클라이언트에서 다음과 같은 요청을 그대로 신뢰하지 않는다.

- 자신의 공격력을 임의로 변경하는 요청
- 실제 획득하지 않은 아이템 추가
- 경험치 및 레벨 증가
- 재사용 대기시간 무시
- 정상적인 경로를 거치지 않는 순간이동
- 건설 재료 없이 건물 설치
- 거래 상대방의 동의 없는 자원 이전

클라이언트는 입력, 화면 표시, 애니메이션 및 사용자 인터페이스를 담당한다.

서버는 실제 게임 결과를 검증하고 확정한다.

싱글플레이와 온라인 사이에서 아이템과 크레딧이 무단 복제되지 않도록 한다.

## 9. 계정 및 로그인 시스템

초기 개발 환경에서는 테스트용 계정 또는 제한적인 게스트 세션을 지원할 수 있다.

실제 운영 환경에서는 안전한 사용자 인증 기능을 적용한다.

기본 기능:

- 계정 생성
- 로그인
- 로그아웃
- 캐릭터 생성
- 캐릭터 선택
- 세션 유지
- 중복 로그인 처리
- 연결 종료
- 재접속

계정 정보와 캐릭터 정보를 구분한다.

비밀번호를 평문으로 저장하지 않는다.

가능하면 검증된 인증 라이브러리 또는 관리형 인증 서비스를 사용한다.

서버 비밀키, 데이터베이스 접속 정보 및 인증 관련 비밀값을 프론트엔드 소스에 포함하지 않는다.

개발용 인증 방식은 운영 환경에서 비활성화한다.

실제 서비스에 필요한 인증 환경이 준비되지 않았다면 로컬 개발용 기능과 운영용 미구현 항목을 명확히 구분한다.

## 11. 공동 세계 생성

플레이어가 새로운 온라인 세계를 생성할 수 있도록 한다.

설정 항목:

- 세계 이름
- 최대 플레이어 수
- 공개 여부
- 초대 코드 또는 비밀번호
- 기본 난이도
- 공동 창고 설정
- 건설 권한
- 기지 방어 이벤트
- 플레이어 간 피해 허용 여부
- 신규 참가자의 기본 권한

기본 추천 설정:

- 최대 인원: 4명
- 비공개 세계
- 일반 난이도
- PvP 비활성화
- 허용된 구성원만 건설 가능
- 공동 창고 보호
- 침공 이벤트는 플레이어 접속 중에만 진행

세계 소유자가 로그아웃하더라도 다른 참가자가 정상적으로 플레이할 수 있는 서버 기반 구조를 목표로 한다.

서버가 종료되는 경우 세계 상태를 안전하게 저장한다.

## 12. 친구 초대 및 방 참가

친구를 초대하기 위한 기능을 제공한다.

- 고유 초대 코드 생성
- 초대 코드 복사

- 참가 권한 확인
- 초대 만료
- 초대 취소
- 세계 참가 승인

초대 코드는 예측하기 어려운 충분히 안전한 방식으로 생성한다.

초대 코드 입력 횟수에 합리적인 제한을 적용한다.

친구가 접속하면 다음 메시지를 표시한다.

"새로운 개척자가 합류했습니다."

참가한 플레이어는 안전한 초기 위치 또는 지정된 공동 기지에서 시작한다.

공동 세계의 현재 행성 진행 상황과 플레이어 개인의 진행 상황을 확인한다.

스토리를 진행하지 않은 플레이어가 후반 행성으로 자동 이동하여 위험에 노출되지 않도록 한다.

## 18. 협동 전투 시스템

같은 탐험 지역에 있는 플레이어들이 동일한 몬스터와 싸울 수 있도록 한다.

몬스터의 위치와 체력, 공격, 상태 이상 및 사망 상태는 서버에서 관리한다.

모든 플레이어에게 동일한 전투 결과가 표시되어야 한다.

기존 무기 시스템을 재사용한다.

- 원거리 투사체
- 근접 공격
- 공중 공격
- 수중 공격
- 충전 공격
- 범위 공격
- 드론 및 소환 장비
- 궁극기

공격의 실제 피해량은 서버에서 계산한다.

한 몬스터가 여러 플레이어에게 동시에 처치되었을 때 경험치와 아이템이 비정상적으로 중복 지급되지 않도록 한다.

기본 협동 모드에서는 플레이어끼리 공격해도 피해가 발생하지 않도록 한다.

아군의 몸체 충돌 때문에 이동 경로가 막히지 않도록 한다.

## 19. 몬스터 AI 및 위협도

온라인 몬스터는 여러 플레이어를 인식할 수 있어야 한다.

다음 요소를 고려하여 공격 대상을 선택한다.

- 플레이어와의 거리
- 최근 받은 피해
- 가디언의 도발 효과
- 회복 및 지원 행동
- 현재 공격 대상
- 지역별 이동 가능 범위

위협도 시스템을 활용하여 적이 너무 자주 공격 대상을 변경하지 않도록 한다.

보스마다 다음 대상 선택 방식 중 일부를 적용한다.

- 가장 가까운 플레이어
- 위협도가 높은 플레이어
- 일정 시간마다 변경되는 대상
- 지정된 영역 전체
- 무작위 유효 대상

몬스터가 로그아웃한 플레이어나 사망한 플레이어를 계속 공격하지 않도록 한다.

모든 플레이어가 지역을 벗어나면 몬스터가 정상적인 복귀 상태로 전환되도록 한다.

## 20. 협동 난이도 조정

기존 싱글플레이 몬스터 및 보스를 협동 환경에 맞게 조정한다.

초기 보스 체력 조정 예시:

| 참여 인원 | 체력 배율 |
|---|---:|
| 1명 | 1.0배 |
| 2명 | 1.6배 |
| 3명 | 2.2배 |
| 4명 | 2.8배 |

위 수치는 실제 전투 테스트를 위한 초기 밸런스 값이다.

참가 인원이 증가한다고 몬스터 공격력을 무조건 동일한 배율로 증가시키지 않는다.

다음 요소를 활용하여 협동 난이도를 차별화한다.

- 추가 공격 패턴
- 동시에 공격하는 대상 수
- 소환 몬스터 수
- 환경 장치
- 역할 분담
- 약점 노출 조건

보스 전투 시작 시 참여 인원을 기준으로 난이도를 확정한다.

전투 도중 참가자가 반복 접속하고 퇴장하는 방식으로 보스 체력을 비정상적으로 조절하지 못하도록 한다.

접속 끊김으로 전투 진행이 어려워진 경우 합리적인 재도전 절차를 제공한다.

## 21. 협동 보상 및 아이템 분배

기본 전리품 분배는 개인 보상 방식을 사용한다.

각 플레이어는 자신의 전리품을 확인하고 획득할 수 있다.

다른 플레이어의 아이템을 빼앗기 위해 경쟁하는 구조를 지양한다.

보상 방식:

### PERSONAL LOOT

개인 전리품.

기본 추천 방식이다.

### SHARED MATERIALS

공동 자원.

공동 개척 임무에서 획득한 일부 건설 재료를 공동 창고에 지급한다.

### CONTRIBUTION REWARD

참여 보상.

전투, 회복, 보호, 탐험 및 임무 수행에 실질적으로 참여한 플레이어에게 보상을 지급한다.

단순히 가장 많은 피해를 준 플레이어만 높은 보상을 받는 구조를 피한다.

지원형 직업과 방어형 직업도 합리적인 보상을 획득할 수 있어야 한다.

아무 행동 없이 안전한 위치에 머무르는 캐릭터가 모든 보상을 반복 획득하는 문제를 방지한다.

고유 스토리 보상은 플레이어별 수령 기록을 관리한다.

## 22. 협동 부활 시스템

온라인 협동 중 체력이 0이 된 플레이어에게 구조 가능 상태를 적용할 수 있다.

상태:

- Alive
- Downed
- Reviving
- Dead
- Respawning

플레이어가 쓰러졌을 경우 파티원이 일정 시간 가까이에서 구조를 진행할 수 있도록 한다.

초기 구조 시간 예시:

- 구조 가능 시간: 20~30초
- 구조 행동 시간: 약 3초
- 구조 후 체력: 최대 체력의 30%

위 수치는 전투 밸런스에 맞게 조정한다.

구조 중 강한 피격을 받거나 구조 범위를 벗어나면 구조 행동이 중단된다.

파티원 전체가 쓰러진 경우 협동 전투 실패로 처리하고 안전한 체크포인트에서 재도전할 수 있도록 한다.

무한 구조를 통한 보스 공략 악용을 방지하기 위해 전투별 구조 횟수 또는 일시적인 재사용 제한을 적용한다.

싱글플레이에서는 기존 부활 시스템을 유지한다.

## 23. 공동 기지 건설

멀티플레이의 핵심 콘텐츠 중 하나는 공동 기지 건설이다.

플레이어는 친구들과 같은 개척지에 건물을 배치하고 시설을 운영할 수 있다.

다음 기능을 서버에서 관리한다.

- 건물 배치
- 건물 철거
- 건설 재료 소비
- 건물 업그레이드
- 전력 연결
- 자동 채굴
- 생산 설정
- 창고 이용
- 연구 진행
- 기지 방어

한 명의 플레이어가 건물을 설치하면 다른 플레이어에게도 동일한 위치의 건물이 표시되어야 한다.

두 명이 같은 위치에 동시에 건물을 설치하려는 경우 서버에서 먼저 승인된 유효한 요청만 처리한다.

승인되지 않은 건설 요청으로 자원이 차감되지 않도록 한다.

건설 모드의 미리보기는 클라이언트에서 표시하되 최종 배치는 서버에서 확정한다.

## 28. 플레이어 간 직접 거래

거래 과정:

1. 상대 플레이어에게 거래 요청.
2. 상대방이 수락.
3. 각자 거래할 아이템과 크레딧 등록.
4. 거래 조건 확인.

6. 최종 거래 승인.

8. 거래 완료 및 양측 아이템 지급.

거래 조건이 변경되면 양쪽 플레이어의 기존 승인을 초기화한다.

거래를 승인한 아이템은 최종 처리 전까지 다른 제작이나 판매에 사용할 수 없도록 예약한다.

거래를 취소하면 예약을 해제한다.

거래 도중 연결이 끊기면 안전하게 거래를 취소하거나 이미 완료된 거래 결과를 복원한다.

다음 아이템은 거래 대상에서 제외할 수 있다.

- 스토리 핵심 아이템
- 고유 보스 인증 데이터
- 귀속된 직업 장비
- 퀘스트 진행용 아이템

다른 행성의 생산 시설은 경량 시뮬레이션으로 운영한다.

플레이어는 서로 다른 행성에서 활동하다가 공동 기지나 우주 정거장에서 만날 수 있다.

지역 이동 중에는 기존 지역 구독을 종료하고 새로운 지역 구독을 시작한다.

이전 지역의 몬스터와 투사체, 플레이어 객체가 화면에 남지 않도록 한다.

우주선 출발 이후 연결이 끊긴 플레이어는 재접속 시 안전한 위치에서 복원한다.

연료는 항해 요청당 한 번만 소비한다.

공동 화물과 개인 인벤토리를 명확하게 구분한다.

### PHASE IV — STELLAR OVERLOAD

- 강력한 에너지 방출
- 보조 기계 소환
- 광역 공격
- 최종 코어 노출

특정 직업이 없으면 해결할 수 없는 기믹을 만들지 않는다.

2인과 4인 모두 공략 가능하도록 동시 활성화 장치 수를 조정한다.

전투 실패 후 재도전할 수 있도록 한다.

## 40. 공동 엔딩 선택

- HARMONY

기본 방식:

- 세계 소유자가 투표 시작.
- 참가 조건을 충족한 구성원이 투표.
- 투표 결과 확인.
- 사전에 설정된 결정 규칙 적용.
- 최종 선택 확인.
- 공동 세계 상태 저장.

세계 소유자 결정 방식 또는 다수결 방식을 세계 설정에서 선택할 수 있도록 한다.

동률 발생 시 처리 방식도 투표 전에 안내한다.

한 번 확정된 엔딩을 일반 구성원이 무단으로 변경할 수 없도록 한다.

어떤 엔딩을 선택하더라도 Phase 9의 핵심 문명 발전 콘텐츠를 이용할 수 있도록 한다.

## 41. 오프라인 공동 세계 운영

- 시설 영구 파괴 방지
- 정착민 대규모 피해 방지

서버가 실제 실행 중인지, 세계가 휴면 상태인지 구분한다.

클라이언트의 로컬 시간이나 사용자 컴퓨터 시간에 의존하여 온라인 생산량을 계산하지 않는다.

동일한 오프라인 기간을 여러 플레이어가 각각 접속할 때 반복 계산하지 않도록 한다.

기존 게임 시스템을 최대한 재사용하고 안정적인 협동 기능부터 확장한다.

실제로 검증하지 않은 최대 동시 접속 인원이나 성능 수치를 달성한 것으로 보고하지 않는다.

외부 배포가 완료되지 않았다면 인터넷을 통한 친구 초대가 실제로 가능한 것처럼 보고하지 않는다.

## 52. 개발 및 실행 방식

기존 싱글플레이 실행 방식을 유지한다.

멀티플레이 개발 환경에서는 다음 기능을 제공한다.

- 클라이언트 개발 서버 실행
- 멀티플레이 서버 실행
- 개발용 데이터베이스 초기화
- 테스트용 계정 또는 게스트 세션 생성
- 테스트 세계 생성
- 서버 연결 상태 확인

가능하면 간단한 명령으로 클라이언트와 서버를 함께 실행할 수 있도록 한다.

예시 명령:

```bash
npm install
npm run dev
```

또는 현재 프로젝트 구조에 따라:

```bash
npm run dev:client
npm run dev:server
```

위 명령은 예시다.

실제 프로젝트의 package.json에 존재하는 실행 명령과 일치하도록 구현한다.

README.md에 코딩 경험이 많지 않은 사용자도 따라 할 수 있도록 한국어로 설명한다.

다음 세 가지 환경을 구분한다.

1. 한 컴퓨터에서 두 개의 브라우저 세션으로 테스트.
2. 같은 네트워크에 연결된 두 컴퓨터에서 테스트.
3. 실제 인터넷에 배포된 서버를 통해 원격 플레이.

한 컴퓨터에서 두 브라우저를 실행하는 테스트에 성공했다고 인터넷을 통한 원격 멀티플레이 배포까지 완료되었다고 보고하지 않는다.

- 새로운 행성에 도착했을 때 탐험의 설렘이 있는가.
- 직업 선택과 성장의 성취감이 있는가.
- 기지를 건설하는 과정이 재미있는가.
- 자동 생산이 실제 편의성을 제공하는가.
- 문명 관리가 지나치게 복잡하지 않은가.
- 친구와 함께하는 플레이가 혼자 하는 것과 차별화되는가.
- 친구를 초대하고 함께 플레이하는 과정이 쉬운가.
- 게임을 종료하고 다시 시작해도 정상적인 진행이 가능한가.

발견한 문제점을 중요도에 따라 분류한다.

### CRITICAL

게임 진행 불가, 저장 손상, 서버 충돌, 자원 복제 및 데이터 유실.

### HIGH

전투 오류, 이동 오류, 퀘스트 진행 불가, 권한 오류.

### MEDIUM

UI 불편, 밸런스 문제, 일부 그래픽 및 사운드 오류.

### LOW

편의성 개선, 추가 연출, 장식 및 세부적인 시각적 문제.

CRITICAL 및 HIGH 문제의 해결을 신규 콘텐츠 제작보다 우선한다.

## 60. 최종 개발 지시

Phase 10의 목적은 ASTROTOPIA를 혼자 즐기는 우주 탐험 RPG에서 친구들과 함께 새로운 문명을 건설할 수 있는 온라인 협동 RPG로 발전시키는 것이다.

다음 우선순위를 가장 중요하게 고려한다.

1. 기존 싱글플레이의 완전한 보호.
2. 실제로 연결되는 온라인 멀티플레이.
3. 안정적인 서버 권한 기반 게임 구조.
4. 자연스러운 캐릭터 및 전투 동기화.
5. 직업별 협동 전투의 재미.
6. 공동 건설과 산업 운영.
7. 자원 및 저장 데이터의 정확성.
8. 친구 초대와 쉬운 접속.
9. 협동 던전 및 보스의 완성도.
10. 향후 대규모 콘텐츠 확장 가능성.

설계 문서만 작성하고 종료하지 않는다.

실제로 실행 가능한 게임 클라이언트와 서버 코드를 구현한다.
